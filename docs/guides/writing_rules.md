# Writing Rules for Project Recaps

## Purpose and Audience
Write a clear, formal recap for readers who need to understand the application and its documented features. Use Indonesian throughout, with simple and direct explanations.

## Accuracy
- Treat screenshots as evidence of the displayed interface and project documentation or implementation as evidence of intended workflows.
- Do not invent features, outcomes, or policies. Check the implementation or project specifications before describing details that are not visible in a screenshot.
- Distinguish implemented features from planned or roadmap items. Do not describe a proposed feature as available.
- Explain data sources, integrations, and demo data accurately, according to each project's documentation and implementation.
- Do not imply that screenshots contain official or live records unless this is verified.

## Structure and Style
- Give each document a specific title and a concise, informative description of the application.
- Organize feature sections in the same order as their screenshot filenames and use matching numbers, including letter suffixes when present.
- Embed each screenshot with useful Indonesian alt text, then add a short paragraph describing only the relevant feature or information visible in the image.
- Expand acronyms on first use when useful, then use domain terms consistently for that project.
- Prefer concrete descriptions over promotional claims, filler, or generic statements about modernity and ease of use.

## Privacy
- Do not copy names, student identifiers, spreadsheet identifiers, credentials, or other personal or confidential values from screenshots into the document.
- Identity facts, including the GitHub profile, come only from [`../profile/MY_PROFILE.md`](../profile/MY_PROFILE.md). Do not add other social links.
- Before public distribution, flag screenshots that visibly contain such values for redaction. Do not alter source screenshots unless asked.
